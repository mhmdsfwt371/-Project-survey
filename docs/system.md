## ١. ما هو النظام

نظام ميداني لإدارة **مسح وتركيب متابعة المشروع** في المشاعر المقدسة لموسم حج ١٤٤٨هـ، من أول زيارة الموقع وحتى اعتماد السيريال هندسيًا. يغطي **١٧٨٧ نقطة**:

| الفئة | العدد | ملاحظة |
|---|---|---|
| مخيمات (مصفوفة `g`) | ١٣٩٢ | منها ١٣١٨ لها شركة موحّدة وتصنيف حجاج (داخل/خارج) |
| ممرات ومحطات وكاميرات وبوابات (مصفوفة `p`) | ٣٩٥ | جمرات، قطار المشاعر، مسجد نمرة، كاميرات الوزارة |
| قائمة انتظار (مصفوفة `q`) | ٠ | محجوزة لنقاط تُضاف لاحقًا بحالة `pending` |

المشاعر: منى، عرفات، مزدلفة، الجمرات، منشآت التسكين، قطار المشاعر، مسجد نمرة. **الحرم خارج النطاق.**

المستخدمون: نحو ١٠ مشرفين ميدانيين و٢٠ فنيًا ومهندسو مكتب وحساب متابعة وزاري.

## ٢. البنية التقنية

- **تطبيق ويب تقدّمي (PWA) من ملف واحد**: كل الشيفرة والبيانات في `index.html` (≈ ٢٫٣ مليون حرف) + عامل خدمة `sw.js` للتخزين المؤقت والعمل بلا اتصال.
- **الاستضافة**: GitHub Pages (مستودع عام — مقايضة مقبولة مقابل استضافة مجانية).
- **الخلفية**: Firebase — مشروع `project-survey-60600` على خطة Spark المجانية:
  - Firestore للمزامنة الفورية بين الأجهزة (مع التخزين الدائم للأوفلاين).
  - Firebase Authentication (بريد/كلمة مرور) لبوابة الدخول.
- **الخرائط**: Leaflet — طبقة CARTO Positron (افتراضية فاتحة) + Esri World Imagery (زر القمر الصناعي). زر «اتجاهات» فقط هو الذي يفتح خرائط جوجل.
- **إكسل**: مكتبة SheetJS مدمجة داخل الملف (لا تحميل من CDN).
- **لا يوجد سيرفر خاص**: كل المنطق يعمل في المتصفح؛ الأتمتة الوحيدة خارج المتصفح هي GitHub Actions (§١٠).

## ٤. دورة حياة النقطة

```
لم يُزر ──مسح──▶ تمت الزيارة ──قرار المكتب──▶ مجدول ──إسناد──▶ فني محدد
                     │                            │
                     ▼                            ▼
              (مناسب / غير مناسب /         قيد التركيب ──▶ مُركّب ──▶ تدقيق هندسي
               مناسب بتعديل)                    │            (سيريال + اعتماد)
                                                ▼
                                             متعذّر
```

**حالتان منفصلتان لكل نقطة** — هذا أهم مفهوم في النظام:

1. **حالة الميدان** `recs[id].fstat` — تلوين الخريطة والقوائم:
   - `new` لم يُزر · `done` تمت الزيارة (تظهر «جاهز للتركيب» في وضع التركيب) · `draft` مجدول · `blocked` تم التركيب · `pending` قائمة انتظار (لنقاط `q` فقط).
2. **حالة التركيب** `inss[id].status` بالعربية:
   - `لم يبدأ` → `مجدول` → `قيد التركيب` → `مُركّب` أو `متعذّر`.

الربط بينهما: عند حفظ التركيب بحالة `مُركّب` يضبط التطبيق تلقائيًا `fstat:'blocked'` في سجل المسح.

**الجدولة**: يضغط المهندس «مجدول» من نافذة النقطة على الخريطة (وضع التركيب) — فتتلون النقطة وتدخل طابور الإسناد.

**الإسناد (V4.0)** — طريقتان:
- **دفعة**: لوحة المتابعة ← «توزيع فرق التركيب» — إسناد مربع كامل من قائمة منسدلة، أو «إسناد نقاط مفردة»: اختيار الفني ← بحث بالشاخص/المربع/المشعر ← تعليم النقاط ← «إسناد المحدد». فلتر «بلا فريق فقط» وزر «تحديد كل الظاهر».
- **نقطة واحدة**: خانة «الفني / الفريق المسؤول» داخل نموذج التركيب نفسه (للمهندس والأدمن).

الإسناد يكتب `inss[id].team` فقط — لا يغيّر الحالة أبدًا، ويُسجَّل في `events`.

**التدقيق الهندسي**: بعد `مُركّب` تدخل النقطة طابور التدقيق — المهندس يُدخل السيريال ويعتمد (`verified:true, qaBy, qaDate`) أو يُرجعها للفريق مع ملاحظة (`qaNote`، وتعود الحالة `قيد التركيب`).

**المواقع المقترحة**: المشرف الواقف على موقع غير مسجّل يفتح «موقع غير موجود» — يفحص التطبيق أقرب ١٤٠ مترًا ويحذّره من المواقع المسجّلة القريبة، ثم يرسل مقترحًا بمعرّف `NEW-MIN-nnn` أو `NEW-ARF-nnn` بحالة `proposed`. السبب `عدم وجود تخصيص` (V4.0) يُعفي من إلزام شركة الخدمة.

## ٥. سجل المواقع المدمج (`DB`)

كائن ثابت داخل `index.html` (سطر واحد ≈ ١٫٣ مليون حرف). **تعديله = تعديل الملف ونشر نسخة.** البيانات الميدانية المتغيرة لا تُكتب فيه أبدًا — بل في Firestore.

```js
DB = { z, t, w, co, dm, g, p, q }
DB.d = [...DB.g, ...DB.p, ...DB.q]   // كل النقاط — فهرس الصف الأول [0] هو المعرّف
```

| المفتاح | المحتوى |
|---|---|
| `z` | المشاعر الستة: منى، عرفات، الجمرات، منشآت التسكين، قطار المشاعر، مسجد نمرة |
| `t` | أنواع المواقع السبعة: مخيم، ممر، كاميرا، جسر، مبنى، محطة، بوابة |
| `w` | أنواع العمل الستة: إعادة تركيب ١٤٤٧، إطار معدني جديد، نقطة ممر جديدة، تفعيل كاميرا قائمة، ترقية كاميرا، خارج النطاق |
| `co` | ٤٢ شركة حجاج خارج (مرجع تاريخي — الحوكمة الحية في `colist`) |
| `dm` | ١٢٠ مشغّل حجاج داخل |
| `g` | صفوف المخيمات (٣٠ عمودًا) |
| `p` | صفوف الممرات والمحطات والكاميرات (٢٨ عمودًا) |
| `q` | قائمة انتظار (فارغة حاليًا — معرّفاتها تُعامل `pending`) |

### أعمدة صف المخيم `g[i]` (٣٠ عمودًا)

| # | الحقل | مثال |
|---|---|---|
| 0 | المعرّف `NSK-{ARF\|MIN}-CMP-nnnn` | `NSK-ARF-CMP-0001` |
| 1 | الاسم المولّد | `عرفات - مربع 7-15 - شاخص 1-3-5/506` |
| 2 | فهرس المشعر في `z` | `1` |
| 3 | فهرس النوع في `t` | `0` (مخيم) |
| 4 | فهرس نوع العمل في `w` | `1` |
| 5، 6 | خط العرض، خط الطول | |
| 7 | مضلّع حدود المخيم `[[lon,lat],…]` | يُرسم على الخريطة |
| 8 | رقم المربع | `7-15` |
| 9 | رقم الشاخص | `1-3-5/506` |
| 10 | اسم الشركة **الخام** من ملفات التخصيص (٣٣ اسمًا مميزًا) | |
| 11 | الجنسية | `مصر - القرعة` |
| 12 | الجهة السيادية (إن وُجدت) | `وزارة الدفاع` |
| 13 | مشغّل حجاج الداخل | |
| 14 | السعة المسجّلة ١٤٤٧ (حاج) | `3263` |
| 15 | نسبة إشغال ١٤٤٧ | `93%` |
| 16 | وجود عائق ١٤٤٧ | `نعم` |
| 17 | عدد حجاج مساند من ملفات ١٤٤٧ | |
| 18 | حالة تركيب ١٤٤٧ | `تم` / `لم يتم` |
| 19 | ملاحظة كهرباء | `كهرباء ومحولات` |
| 20 | أساس شبكة ١٤٤٧ | `172.16.104` |
| 21 | نص المنطقة | `منطقة منى` |
| 22 | حالة أولية ثابتة | `لم يبدأ` |
| 23–25 | **فارغة — لا تُستخدم** (كانت سبب خلل أصلحته V4.1/V4.2) | |
| 26 | تصنيف الحجاج | `داخل` / `خارج` |
| 27 | **الشركة الموحّدة** (١٦٢ اسمًا مميزًا) — المصدر المعتمد للعرض والتقارير | `إكرام الضيف` |
| 28 | تنبيه للمشرف | `المشغّل غير معروف — يُحدَّد ميدانيًا` |
| 29 | علم داخلي | `1` |

**قاعدة قراءة الشركة في كل التطبيق**: `fix.company ← r[27] ← r[10]` (تصحيح المشرف الميداني أولًا، ثم الموحّدة، ثم الخام).

### أعمدة صف `p[i]` (٢٨ عمودًا)

معبأة فقط: `0` المعرّف (`NSK-ARF-COR-…`، `NSK-TRN-STN-…`، `NSK-JMR-PNT-…`، إلخ)، `1` الاسم، `2–4` الفهارس، `5–6` الإحداثيات، `19` نص المنطقة، `20` `لم يبدأ`. الباقي فارغ — قراءات أعمدة المخيمات عليها تُرجِع فراغًا بأمان.

### اشتقاقات مهمة

- `szOf(r)` — المشعر التقريري (منى/عرفات/مزدلفة): الجمرات ومنشآت التسكين ← منى؛ مسجد نمرة ← عرفات؛ قطار المشاعر حسب اسم المحطة.
- `catFull(r)` — ١٦ فئة منطقية بترتيب ثابت للتقارير والتصدير (مخيمات منى، ممر منى، قطار منى، جمرات منى، كاميرات منى، منشآت التسكين، مخيمات/ممر/قطار عرفات، مسجد نمرة، مخيمات/ممر/قطار مزدلفة، قطار المشاعر، مواقع مقترحة، أخرى).
- `ptypeOf(r)` — تصنيف الحجاج: `fix.ptype ← r[26]`.
- `nskIPs(subnet)` — من أساس `a.b.c` يشتق: راوتر `.1`، قارئ `.2`، كاميرا `.3`، والشبكة `a.b.c.0/24`.
- صيغة الشاخص: `SIGN_RE = /^\d+(?:-\d+)*\/\d+$/` إلزامية للمخيمات (مثال `57/2` و`1-3-5/506`)، و`SIGN_LEGACY` تسمح بحروف لاتينية لغير المخيمات. **في إكسل تُصدَّر أعمدة الشاخص نصًا مُجبرًا** حتى لا يحوّل إكسل `1/519` لتاريخ.

## ٦. كولكشنز Firestore

| الكولكشن | معرّف المستند | يكتب | المحتوى |
|---|---|---|---|
| `recs` | معرّف الموقع | مشرف+ | سجل المسح |
| `inss` | معرّف الموقع | مشرف+ | سجل التركيب |
| `props` | `NEW-MIN-nnn` / `NEW-ARF-nnn` | مشرف+ | المواقع المقترحة |
| `photos` | `{kind}__{siteId}__{encodeURIComponent(k)}` | مشرف+ | صورة لكل مستند |
| `settings` | `goal` · `teams` · `stock` · `devices` | إدارة | إعدادات مشتركة |
| `colist` | مفتاح مشتق من اسم الشركة | إدارة (+ إنشاء مشرف بشرط `st:'req'`) | حوكمة قائمة الشركات |
| `events` | تلقائي | إضافة فقط | سجل الأحداث |
| `users` | `uid` | أدمن (المهندس: مشرفين فقط) | الحسابات |

### سجل المسح `recs[id]`

`{id, status:'draft'|'done', fstat, fit:'مناسب'|'غير مناسب'|'مناسب بتعديل', v:{…}, fix:{…}, chal:[…], photos:{i:dataURL}, gps, loc, date:'YYYY-MM-DD HH:mm', by, log:[{d,s,by}]}`

- `v` — ٥٤ حقل قياس معرّفة في قاموس `FIELD_AR` (الأبعاد، الكهرباء، الأطقم، السيناريو…). القائمة الكاملة بأسمائها العربية في `api-schema.json`.
- `fix` — تصحيحات المشرف للبيانات المسجّلة (`name, square, sign, ptype, company, nat, permit, cap, subnet`) — **لها الأولوية على `DB` في كل مكان**.
- `chal` — تحديات من قائمة المخيمات (١١ خيارًا) أو الممرات (٩ خيارات) + «لا توجد تحديات».
- صور المسح ٩ خانات ثابتة (لقطة عامة، نقطة التركيب، الكهرباء، مسار الكابل، شمال، جنوب، الارتفاع، العائق، اختبار الشبكة).

### سجل التركيب `inss[id]`

`{id, status, sched, date, by, done_date, team, serial, verified, qaBy, qaDate, qaNote, v:{kits_done, ins_note}, photos:{0:قبل,1:بعد,2:لوحة الرقم}, log:[{d,s,by}]}`

- `team` — الفني/الفريق المُسند (V4.0). أسماء الفرق في `settings/teams` — **اسم الفريق المطابق لاسم حساب المشرف يُفعّل له زر «جدولي»** تلقائيًا.
- صورة «بعد التركيب» إلزامية لحالة `مُركّب`.

### الموقع المقترح `props[id]`

`{id, zi, lat, lon, acc, v:{region, stype, square, sign, company, company_req, tents, reason, why}, photos, status:'proposed', label, date, by, log}`

أسباب الاقتراح: مخيم جديد لم يكن موجودًا · مخيم انقسم · **عدم وجود تخصيص** (يُعفي من الشركة) · تغيّر ترقيم الشاخص · الشاخص مفقود · سبب آخر. صورة الشاخص إلزامية. صور المقترح ٥ خانات.

### الصور — `photos` منفصلة

**القاعدة الذهبية: لا صورة تُضمّن داخل مستند السجل أبدًا** (حد المستند 1MB). عند الرفع يفصل `NSKSYNC` الصور: السجل يُرفع بلا `photos` ومعه `phN` (عددها)، وكل صورة مستند مستقل `{kind, site, k, d, _up, _by}`. الصورة الأكبر من **٩٨٠٬٠٠٠ حرف** تبقى على الجهاز فقط. عند الاستقبال يعيد `applyPhotoSnap` تركيبها عبر مخزن مؤقت `PHBUF`.

### الإعدادات `settings/*`

- `goal`: `{deadline, regions:{مشعر:تاريخ}, types:{نوع:دقائق-للنقطة}}` — بطاقة الوتيرة والهدف.
- `teams`: `{list:[أسماء الفنيين/الفرق]}`.
- `stock`: `{tot, iss:{فريق:عدد}}` — عُهدة القارئات.
- `devices`: `{list:[{s:سيريال, n:اسم}], n, at, src}` — يغذّيه بوت الأجهزة أو الاستيراد اليدوي.

### حوكمة الشركات `colist`

`{name, st:'req'|'ok', by, at, site?, okBy?, okAt?}` — المشرف **يطلب** (`st:'req'`) من داخل قائمة اختيار الشركة نفسها، والمهندس يعتمد (`st:'ok'`) أو يضيف مباشرة. هذا يمنع انحراف الأسماء في الميدان.

### سجل الأحداث `events`

`{t:serverTimestamp, by, role, txt≤240}` — إضافة فقط، لا تعديل ولا حذف. يعرض آخر ٥٠٠ حدث مع فلاتر تاريخ وبحث حر وتصدير إكسل (١٠ أعمدة تشمل المشعر والفئة).

## ٧. المزامنة والعمل بلا اتصال

- **محليًا**: كل سجل يُحفظ فورًا في تخزين الجهاز بمفاتيح `rec:{id}` · `ins:{id}` · `new:{id}` — يعمل التطبيق كاملًا بلا إنترنت.
- **سحابيًا**: `NSKSYNC.push(kind,id,rec)` يكتب المستند **استبدالًا كاملًا** (`setDoc` بلا دمج) ويضيف `_up` (طابع خادم) و`_by`. `del` يحذف. `log(txt)` يضيف حدثًا. حساب `viewer` لا يرفع شيئًا.
- **الاستقبال**: `onSnapshot` حي على الكولكشنز السبعة + استعلام آخر ٥٠٠ حدث. شريحة حالة أعلى الشاشة تبيّن (متزامن / جارٍ الرفع / انقطاع).
- **كوتة Spark**: ٢٠٬٠٠٠ كتابة يوميًا — أضعاف الاستخدام الميداني المتوقع. **العدّاد يتصفّر نحو ١٠–١١ صباحًا بتوقيت السعودية** وليس منتصف الليل.

## ٨. قواعد الأمان (`firestore.rules`)

- `isBoss` — بريد الأدمن الدائم. `ok` — مسجّل ومستنده `active:true`. `mgr` — مهندس/أدمن. `canW` — مشرف فأعلى.

### إعادة الضبط — تصفير مُتحقَّق منه (V6.6)

كان المسح المحلي يمرّ على `Object.keys(NSKCORE.all(kind))` — أي **ما هو في الذاكرة فقط**. أي مفتاح في التخزين لم يُحمَّل (فشل تحميل، أو بقايا جلسة سابقة) كان ينجو ويعود بعد إعادة التحميل.

الآن لكل نوع: تُمسح مفاتيح الذاكرة، **ثم يُكنس التخزين بـ `storage.list(prefix)`** فيُحذف كل مفتاح باقٍ بذلك البادئة. وتُمسح كذلك `nsk.seen` و`nsk.dtab`.

وبعد المسح يُستدعى `wipeVerify()` الذي يفحص الذاكرة والتخزين وقائمة ما ينتظر الرفع، فإما «كل الأرقام صفر ✓» أو رسالة تسمّي ما تبقّى ومكانه — وتُسجَّل النتيجة في سجل الأحداث.

**لا يُمسح عمدًا:** حسابات المستخدمين، قائمة الشركات المعتمدة، وسجل الأحداث (أثر تدقيقي).

### مؤشّر المزامنة (V6.5)

كان `sysChecks().pend` يعدّ كل سجل لا يحمل `synced === true` — و**`synced` لم تكن تُكتب في أي موضع من الشيفرة**، فكان العدّاد يساوي دائمًا عدد السجلات كلها مهما نجحت المزامنة. لم يكن مؤشّرًا بل عدّادًا للسجلات.

الآن:

| | |
|---|---|
| عند بدء الرفع | `rec.synced=false` و`rec.syncTry++` |
| عند نجاح `setDoc` | `_markSynced(kind,id,true)` → `synced=true` و`syncAt` بالوقت، ثم `save()` وتحديث اللوحة |
| عند الفشل | `_markSynced(kind,id,false,err)` → يُحفظ سبب الفشل في `syncErr` |

`unsyncedList()` يعيد كل تغيير غير مؤكَّد من `recs` و`inss` و`props` مرتبًا بالأحدث، ولكل صف: نوعه ومعرّفه و**من أنشأه** (`by` أو `_by`، و«غير معروف» إن غابا) وتاريخه وعدد محاولاته وسبب تعثّره. و`retrySync()` يعيد رفع الجميع ثم يُبلّغ بما تبقّى.

### ما يظهر في لوحة الإدارة (V5.9)

فتح نموذج موقع وتعديل حقل فيه يُنشئ سجلًا بحالة `draft` فورًا — حتى لو خرج المستخدم دون تسجيل الزيارة. قبل V5.9 كان هذا السجل يظهر في لوحة الإدارة فيبدو الموقع «مزارًا» وهو لم يُزر.

`isVisited(r)` تحكم الظهور:

| الحالة | يظهر؟ | لماذا |
|---|---|---|
| `fstat` = `done` أو `blocked` | ✅ | وُسم على الخريطة تمت الزيارة أو تم التركيب |
| `status` = `done` | ✅ | حُفظ السجل مكتملًا |
| `status` = `blocked` | ✅ | متعذّر الوصول — قرار ميداني موثّق |
| `status` = `proposed` / `pending` | ✅ | المقترحات مسار مستقل مساره الاعتماد لا الزيارة |
| `status` = `draft` بلا `fstat` | ❌ | مسوّدة ناقصة — لم تكتمل زيارتها |

المخفيّ لا يُفقد: شريط أعلى الجدول يعرض عددها ومعه زرّان — «إظهار» يضمّها للعرض (`MG_DR`)، و«حذف نهائيًا» (`wipeDrafts()`) يزيلها محليًا وسحابيًا مع صورها بعد تأكيد. الموقع نفسه لا يُمسّ ويظل قابلًا للمسح من جديد.

`draftIds()` يعيد معرّفات هذه السجلات، ويُستخدم في ثلاثة مواضع: شريط لوحة الإدارة، ومعاينة إعادة الضبط التي صارت تكتب «٣ سجل مسح (منها ١ مسوّدة ناقصة)»، وقسم سلامة البيانات الذي ينبّه بعددها ويدلّ على مكان تنظيفها.

### قاموسا الحالة — لا يُخلطان (V5.7)

للموقع حالتان مستقلتان تمامًا، ولكل منهما قاموسه:

| | الحقل | الدالة | القيم |
|---|---|---|---|
| **الحالة الميدانية** | `recs[id].fstat` | `st(id)` → `SL[...]` | لم يُزر · تمت الزيارة · مجدول للتركيب · تم التركيب · مقترح · بانتظار تحديد الموقع |
| **اكتمال السجل** | `rec.status` | `rlbl(rec)` → `RSL[...]` | مسوّدة — ناقصة · مكتمل · متعذّر الوصول · مقترح · بانتظار تحديد الموقع |

المفتاح نفسه يعني شيئين مختلفين: `draft` في الأول «مجدول للتركيب» وفي الثاني «مسوّدة»، و`blocked` في الأول «تم التركيب» وفي الثاني «متعذّر الوصول». قبل V5.7 كانت لوحة الإدارة ونافذة التفاصيل والتصدير تترجم `rec.status` بقاموس `SL` — فسجل مسوّدة يظهر «مجدول للتركيب» بينما الخريطة تقول «لم يُزر». الآن الجدول يعرض العمودين منفصلين، والتصدير يحمل الحالة الميدانية.

**إشعار الشركات (V5.0 · مُحسَّن V5.4)** — قسم `conote` في تبويب التخطيط. الأرقام تُدار بمنتقٍ من القائمة الموحّدة (`coKnown()` = أسماء العمود ٢٧ + المعتمد في `colist`) فيستحيل أن يُكتب اسم لا يطابق، مع إضافة يدوية وقائمة تعرض لكل رقم «✔ مطابق» أو «اسم غير مطابق» وزر حذف. الاستيراد يبلّغ بعدد المطابق وغير المطابق بدل الصمت. يجمع النقاط بحالة `مجدول` لكل شركة مع أقرب موعد، ويرسل رسالة رسمية تسرد مواقعها مرتبة بالموعد الأقرب. الأرقام في `settings/cocontacts` تُستورد من إكسل/CSV باكتشاف تلقائي لعمود الرقم وتحويل `05xxxxxxxx` إلى `9665xxxxxxxx`.

المشكلة قبل V5.5: التطبيق المثبَّت كان يظل على نسخة قديمة رغم إعادة الفتح، لأن طلب الصفحة داخل عامل الخدمة كان يُخدَم من كاش المتصفح نفسه قبل أن يصل للشبكة.

الحل بثلاث طبقات:

1. **في `sw.js`** — الصفحة تُجلب بـ `new Request(url, {cache:'reload'})` فتتجاوز كاش المتصفح تمامًا.
2. **في التسجيل** — `{updateViaCache:'none'}` + `reg.update()` عند الإقلاع وكل ١٠ دقائق + إعادة تحميل واحدة عند `controllerchange`.
3. **شريط صريح** — `nskCheckUpd()` يجلب `sw.js` بـ `no-store` ويقارن `CACHE` بنسخة الهيدر. عند الاختلاف يظهر شريط ذهبي أعلى الشاشة: «نسخة جديدة V5.5 جاهزة». الضغط على «تحديث الآن» يستدعي `doUpdate()`: يمسح كل الكاشات، يلغي تسجيل كل العمال، ثم يعيد التحميل بمعامل زمني.

يُستدعى الفحص تلقائيًا بعد ٢٫٥ ثانية من الإقلاع، وعند عودة التطبيق للواجهة (`visibilitychange`)، ويدويًا من زر «🔄 فحص التحديثات الآن» في تبويب الرفع.

## ١٣. الأتمتة — GitHub Actions

| السير | الجدول | يفعل |
|---|---|---|
| `backup.yml` | يوميًا `30 2 * * *` UTC = **٥:٣٠ صباحًا KSA** | يقرأ كل الكولكشنز بمفتاح خدمة ويكتب `backups/latest/{collection}.json` ثم يعمل commit — تاريخ git هو أرشيف النسخ. `photos` تُحصى عددًا فقط |
| `devices.yml` | كل ٦ ساعات | يجلب سجل الأجهزة من نظام العميل ويكتب `settings/devices`. **يخرج بهدوء** إن لم تُضبط الأسرار (`DEVICES_API_URL`, `FIREBASE_SERVICE_ACCOUNT`)؛ التهيئة عبر متغيرات: `DEVICES_AUTH_HEADER/PREFIX`, `DEVICES_JSON_PATH`, `DEVICES_FIELD_SERIAL/NAME`, `DEVICES_NAME_FILTER` |

**ملاحظة تشغيلية للنشر اليدوي**: بوت النسخ يعمل commit ليلي — لذلك قبل أي push: `git fetch` ثم `git rebase origin/main` وإلا رُفض الدفع.

## ١٤. القواعد الحاكمة للمشروع

1. **الاستقرار قبل التحسين** أثناء الموسم — الترحيل للدومين الخاص وإعادة الهيكلة ونقل النسخ لريبو خاص كلها **مؤجّلة لما بعد الموسم**.
2. **الإصدار**: كل نشر يرفع الرقم في هيدر التطبيق («نسخة Vx.x») وفي سلسلة `CACHE` داخل `sw.js` — بدون الثانية لا يصل التحديث للأجهزة.
3. **المصطلح**: «شاخص» لا «شاخصة» — مع الحفاظ على مطابقة الجنس النحوي في الجمل المحيطة.
4. **الشركات**: الاختيار من القائمة الموحّدة فقط؛ الجديد يمر بمسار `colist`.
5. **الصور**: منفصلة دائمًا في كولكشن `photos`.
6. **أعمدة السجل**: البيانات المرجعية للمخيمات في `26/27/28` — لا تقرأ من `23/24/25` (فارغة).
7. **التوكنات**: لا يُكتب أي توكن في المستودع لأنه عام.
8. **تطابق التوثيق**: مع كل إصدار تُرفع في نفس الدفعة `index.html` و`sw.js` و`docs/api-schema.json` و`docs/system.md` و`docs/nusuk-guide.docx` **بنفس رقم النسخة**. يفرضه `scripts/check-version.mjs` وسير `docs-check.yml` — أي تفاوت يُفشل البناء.

## ١٥. جسور المطوّرين (داخل الصفحة)

```js
NSKCORE.db()                // كائن DB الخام
NSKCORE.all(kind)           // recs | inss | props | colist | settings — الخريطة كاملة
NSKCORE.get/set/rm(kind,id)
NSKCORE.szOf(r)             // المشعر التقريري
NSKCORE.tyOf(r)             // اسم الفئة المنطقية
NSKCORE.total()             // 1787
NSKCORE.redraw()            // إعادة رسم كل الشاشات

NSKSYNC.push(kind,id,rec)   // رفع + فصل الصور + تسجيل حدث
NSKSYNC.del(kind,id)
NSKSYNC.log(txt)            // حدث ≤ 240 حرفًا

NSKDASH.open/close/refresh  // لوحة المتابعة
NSKCATX.order/of/cmp        // الفئات الـ16 وترتيبها
nskIPs(v)                   // {cidr, router, reader, camera} أو null
```

اختبارات المنطق قبل كل نشر تحاكي هذه الواجهة بكائنات وهمية في Node — انظر نمط `mock` في تاريخ الجلسات.

## ١٧. المؤجّل لما بعد الموسم

- ترحيل الدومين وإضافة النطاقات المصرّح بها في Firebase.
- نقل النسخ الاحتياطية لمستودع خاص.
- إعادة هيكلة الملف الواحد إلى وحدات.
- المرحلة الثالثة: خلاصة الأحداث الحية (`events-feed`).
